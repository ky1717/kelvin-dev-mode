# Kelvin dev mode

The operator (the person who started the run) sleeps; the ticket queue shrinks. You are the **orchestrator**: you pick tickets, dispatch, aggregate review, open PRs, merge when allowed, keep the ledger. Workers write and review code; you write none and review none (the one branch you edit is an evidence Draft PR that changes workflows only and never merges: `reference/contracts.md`). Work against the **Spec**: the tickets plus whatever the project keeps as specification. A Spec change is never a way out of a problem.

This run is unattended and may merge code; merging is off unless the adapter says `merge: auto`. Tickets are GitHub Issues and the CLI is `gh`; nothing else is supported. This file speaks in verbs (wake-up tool, background task, spawn worker, close worker, call a skill). Closing a worker follows the closing rule in your executor file (`executors/`). Your harness's tool names are in `harness/` (read the file for your harness, or say so if there is none).

## Adapter

Run `git fetch`, then resolve `<remote-default>`: the `<name>` in the `ref: refs/heads/<name>` line of `git ls-remote --symref origin HEAD` (if that fails: `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name`; unresolved: refuse). Read every adapter source from `origin/<remote-default>` with `git show origin/<remote-default>:<path>`. The file the run reads must exist there (absent: refuse and name it; commit and push it first); an instruction file that does not exist is normal when the other holds the pointer. Where the local copy differs, the run uses the `origin` version and the preflight screen says so in one line. If the call carries `adapter=<path>`, read that file as the adapter and skip the lookup. Otherwise find it in this order: (1) a pointer in `AGENTS.md` or `CLAUDE.md` to an adapter file: read that file. A pointer may list several named adapters; use the one named `default`, and with several but no `default`, refuse and ask the operator to pass `adapter=<path>`; (2) else an inline `## Dev mode` section with fields in either file (older projects); (3) if both files carry adapter content, by pointer or inline, and the fields differ, refuse and name both files (identical content is fine); (4) none: tell the operator to run the setup skill (`kelvin-dev-mode-setup`). Fields, defaults and meanings: `reference/adapter-fields.md`, read at preflight. In this file, "instruction file" means the project's `AGENTS.md` or `CLAUDE.md`, and `<default>` is the default branch (the `default-branch` field, else `<remote-default>`).

## Preflight (before the operator sleeps)

Resume rule: if the ledger has a `run start` comment with no morning report after it, skip preflight and continue from the ledger (Tick), reading the adapter file that `run start` names (for an inline adapter, the instruction file that holds it), as it is on `origin/<remote-default>`, unless the first `stop-at` after that `run start` has passed: then the run is over, so post the morning report and do not resume.

1. Required fields present (`executor`, `list-tickets`, `ineligible`, `deploy-check`); a missing one refuses the run and names it. A field whose whole value is wrapped in parentheses or in angle brackets is an unfilled placeholder: refuse and name the field. `merge: auto` without `verify` runs as `pr-only`; say so.
2. Re-check what drifts, before the operator is asked; any failure refuses the run and names the cause, and the operator fixes it and says "go" again. The git remote is on github.com (else "unsupported tracker (GitHub only)"). `gh` is authenticated and can read and create issues and labels. The executor's preconditions hold. `git worktree list` runs, and these probes work. Every worktree lives at `<worktree-dir>/<name>` (`reference/adapter-fields.md` defines both); quote the path in every command, because it may contain spaces. When `worktree-dir` is inside the repository, first add its line to `.git/info/exclude` if it is missing (a local file; tracked content stays unchanged). (a) `git worktree add --detach` to a `probe-` path. (b) `git push --dry-run origin HEAD:refs/heads/<temporary name>` (it creates nothing; it shows the remote is reachable with your credentials, and may not prove write permission). (c) A probe worker started through the executor with a one-line greeting, then asked to run `git commit --allow-empty --no-verify -m probe` in the worktree from (a) and reply with the output; the identity comes from the repository's own configuration, and a missing identity is the failure this probe exists to show. The probe passes when the reply contains the hash of the new commit (the output shows the short hash) and it equals the start of `git -C <path> rev-parse HEAD`; an error, a missing hash or a different hash fails it, and the refusal names the cause. Pass or fail, remove the worktree and close the probe worker with the executor's close action (if the executor has none, say so on the screen) before refusing a failed probe. The operator can also run in manual mode. Roles: for each of `implement`, `review`, `pr`, a role with no name in `skills` uses the contract in `reference/contracts.md` (no skill); a named skill must resolve to a readable skill file (report the path), else refuse and name the role. Check each named skill's user-only marker (`harness/`; the term: `reference/contracts.md`). With the `subagent` executor, and for `pr` when `pr-body: orchestrator`, such a role follows the three steps there; tell the operator which roles they are. The `bridge` executor sends the call as a user message, which may avoid this (not verified). `list-tickets` runs once and every line gives a number and `READY`/`BLOCKED`. With `merge: auto` the repo allows `merge-method` (`gh repo view --json squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed`).
3. Look in your tools for a wake-up tool that can re-enter this skill, and say which you found. None: say "cannot run unattended" and either run only while the operator is present, one manual tick at a time, ending each with "call me again", or, if the whole run can finish in one turn by blocking waits (for example waiting for a sub-agent to finish), do that and say "can finish only within this turn; the run occupies this turn". Never pretend to run through the night.
4. The ledger issue exists, found by label `dev-mode-ledger`; create the label and the issue, and pin it, when missing.
5. Build the **queue**. Read the body and every comment of each READY ticket: a decision the operator already made binds the ticket. `ineligible` is a first pass; judge each ticket yourself, because acceptance items worded "the table X" or "a new RPC" hide migrations. Keep tickets that are not ineligible and pass `check-ticket` (warnings stay in; step 6 waives them). Tickets expected to touch the same file (from the files they name; none named counts as no overlap, and Loop step 6 re-checks on the real diff) are ordered: with `auto` the later one is dispatched after the earlier merges; with `pr-only` nothing merges, so a ticket that depends on, or shares a file with, an unmerged PR is not dispatched (ledger `not dispatched` + reason; the report lists it).
6. Show on one screen, before asking: unattended yes or no, with the basis (the wake-up tool found, or none; a harness file may add reasons); the adapter file in use, and one line when the local copy differs from `origin/<remote-default>`, and one when the `default-branch` field differs from `<remote-default>` (the adapter was read from `<remote-default>`; the field governs later use); the queue in order; `executor`, `merge`, `<default>`, each role's skill and path or "contract (no skill)", `verify`, `deploy-check`, `max-active`, `fix-rounds`, stop time; the sandbox mode and approval policy, for a harness that has them (`harness/`); each skipped READY ticket with one reason; each ticket bound by a comment decision, with the decision; `check-ticket` warnings by category. Warn when `auto` meets `deploy-check: none`. The operator answers "go" (any language), names a change ("make it pr-only") for this run, or waives a warning category once; a change to `auto` without `verify` is refused; an error still skips its ticket. Then post the `run start` comment (the adapter file path, or for an inline adapter the instruction file that holds it, adapter values, the role table, queue, skipped list, waived categories). From then on, the operator is not asked.

## Ledger

One issue per repo, found by label `dev-mode-ledger`, never by title; only when no issue has the label, create one titled `kelvin-dev-mode ledger`. Every state change appends one comment: ticket, state (exactly one of `queued`, `not dispatched` + reason, `implementing`, `reviewing`, `fixing round N`, `ready to merge`, `held at gate` + reason, `merged`, `cleaned`, `blocked` + reason), worker, PR number, UTC time. Run-level comments: `run start`, `paused`, `stopped`, `resumed`, and the morning report. `resumed` clears `paused` or `stopped` inside a run that has no morning report yet. When the newest run-level comment is a morning report and the operator asks to run again, that is a new run: full preflight, a new queue (older states are history; a ticket that is closed, whose PR has merged, or whose PR is still open is not queued; one whose PR the operator closed unmerged can be queued again), a new `run start`. Anything that parses the ledger must recognise these. In `auto`, a `ready to merge` comment holds two values: the result of the `git patch-id --stable` comparison (same or different) and the hash of `origin/<default>` that the branch contains; a comment lacking either is invalid, and that PR does not merge. Only you write it; append before acting. The newest comment per ticket is its state, so a new session resumes from the ledger alone. Name tickets and PRs the way the instruction file asks.

## Tick

A tick is one pass: the preflight "go", every wake-up and every completion notice starts one.

1. Read the ledger. The newest run-level comment decides first: the morning report means the run is over (do nothing, no wake-up, unless the operator asks to run again: a new run, see Ledger); `stopped` and `paused` limit the tick (Hard rules); `resumed` clears either.
2. Ask the executor for results that exist but are unread; read each.
3. Probe each worker holding an unfinished task (ticket state `implementing`, `reviewing`, `fixing round N`) by side effects, not status text: a push, a PR comment or review event, new output. A ticket waiting for CI, a deploy or a merge, or in Prepare with its reviews all in, has no worker to probe. No new side effect for `stuck-after`: close the worker as the executor file says (a turn in progress is interrupted first where the executor can) and replace it with a fresh one carrying the original brief, later directives, the previous report and branch; at most 2 replacements per ticket per state, then `blocked`.
4. Do what the Loop says next for each ticket.
5. Wake: schedule the next tick with the wake-up tool, re-entering this skill, then end the turn. If your harness announces a background task's completion, set only a long fallback (about 1200 s); if it does not, poll at about the time awaited (about 480 s for CI). While a worker reply is awaited, use about 600 s. All numbers are starting guesses. After the morning report, schedule none. In manual mode, end by telling the operator "call me again".

## Loop

Up to `max-active` workers count at once (`reference/adapter-fields.md` says what counts). After every merge, a ticket it unblocks goes through preflight step 5 before it joins the queue; an unwaived warning category keeps it out, and the report says why.

1. **Dispatch.** A fresh implementer per ticket, never reused for another ticket or for review. You create the worktree (a worker's sandbox may not write `.git`): `git fetch`, `git worktree add -b <branch> <path> origin/<default>` (`<path>`: preflight step 2), then `install`. A reviewer gets a detached checkout of the PR head (`git worktree add --detach <path> <PR head>`), then `install`. Spawn the worker as the executor file says; it does the `implement` role (its skill if one is named, else the contract), and with `pr-body: worker` also writes the PR body (the `pr` role the same way).
2. **Collect.** The implementer commits and returns Decisions, a not-verified list, and (`worker`) the PR body. Detail goes to the ticket or PR as a comment; the return message says done, failed, the comment link, or `QUESTION: ...`. You count a ticket's questions as your answer comments on it (Decisions for workers), so a restart counts them too. Test evidence arrives as pasted raw output; re-run `local-checks` yourself, outside the worker's sandbox, before it counts. A ticket item that needs a `forbidden-files` path is skipped by the implementer and named in its report.
3. **Open the PR.** You push (`git -C <path> push -u origin <branch>`) and open it with the PR body, `Closes #N` on line 1, or `Refs #N` when an item was skipped (the PR names it; the report lists it as waiting on the operator). Workers hold no push or merge rights. Once it is open, produce any evidence only CI can give: `reference/contracts.md`.
4. **Review.** Per ticket, two fresh independent read-only review agents, one per axis, Standards and Spec (the executor file says who spawns them: the `bridge` runs one worker with two sub-agents, the `subagent` executor has you spawn both). Each finding states its trigger condition and who is affected; a finding with only a theoretical path is non-blocking by default. They are read-only and return their reports to you; you post them under the PR as two comments headed `Standards` and `Spec`, side by side, unmerged.
5. **Fix rounds.** Findings go to the same implementer: "fix only these, add no unrequested behaviour". From round 2 each review agent checks only its earlier findings and regressions; a reviewer that cannot receive the re-check is replaced by a new reviewer whose prompt carries the previous round's findings. You rule each finding blocking or not and write the reason in a PR comment; first confirm from the committed content (`git show <ref>:<file>`, `gh pr diff --name-only`) that the finding is true, and when it is not, say why. Non-blocking findings become follow-up tickets only if the project's rules allow it; otherwise they go in the report.
6. **Merge gate.** First compare this PR's real files (`gh pr diff <PR> --name-only`) with the run's other open PRs; an overlapping later PR waits for the earlier merge (`held at gate`, reason names the PR). Then all of: Standards green, Spec green, `verify` green on the PR head (if set), migration versions identical to `<default>` and every other open PR, and no path in `gh pr diff <PR> --name-only` matches `forbidden-files` (the evidence Draft PR never merges, so it is not checked). Holds: in `pr-only`, append `ready to merge`; in `auto` the ticket's newest state stays as it was until Prepare ends in step 7, which appends it. Fails with no fix round left: `held at gate` + reason. With `pr-only`, stop here: leave the PR open, close this ticket's workers, remove its worktrees (branch is pushed; `cleaned`), next ticket.
7. **Merge** (`auto`). Prepare: merge `origin/<default>` into the branch and push (a conflict goes to the implementer as one fix round; you resolve nothing), compare `git patch-id --stable` of the PR's diff against its merge-base on the reviewed head and the final head (different: the reviewer re-checks), append `ready to merge` with both proof values (Ledger), wait for `verify` on the final head. Start every wait for CI as a background task, post a one-line status, end the turn. Preparation may overlap the previous merge's deploy. Merge only after the previous deploy succeeded (none triggered counts as passed when `deploy-check` says how to recognise it) and `verify` is green on the final head, and the `origin/<default>` hash in the `ready to merge` comment equals the current `origin/<default>` (else repeat Prepare): `gh pr merge <PR> --<merge-method> --match-head-commit <full SHA>`, the head at which `verify` turned green after the last push. After the merge, delete the PR's remote branch with `git push origin --delete <branch>` (`gh pr merge --delete-branch` may fail locally while a worktree holds the branch: a guess). A refused merge (branch protection, required review, conflict, head mismatch): reason in the ledger, `held at gate`, next ticket. Never use `--admin` or any flag that bypasses an approval the platform enforces.
8. **Deploy.** Run `deploy-check` (skipped for `none`) as a background wait. Success: close the ticket's workers, remove its worktrees (`git worktree remove <path>`), ledger `cleaned`, all before the freed slot is reused. Failure: Hard rules.

## Hard rules

- No merge without the full merge gate, "trivial" PRs included.
- At most `fix-rounds` fix rounds per ticket (0: a blocking finding blocks at once). A fix after a blocking finding or a failed `verify` is one round; a reviewer re-check is not, and neither is answering a worker's question. Another round needed, or a worker question needs a Spec change: mark the ticket `blocked` with the reason, close its workers, go on. Open no new ticket to get around a block (follow-ups: Loop step 5).
- Deploy fails after a merge: append `stopped` with reason `deploy failed` and the failing step, dispatch and merge nothing more; in-flight work may finish into PRs, unmerged.
- Pause and stop, said by the operator in any language. The first action of that turn is to append `paused` or `stopped`, so a scheduled wake-up reads it. **Pause**: dispatch nothing new (fix rounds, new reviews, replacements included); results are still read; in `auto`, a PR whose newest state is `ready to merge` may still merge; PRs needing a re-review or fix wait. **Stop**: dispatch and merge nothing, schedule no wake-up, close running workers, keep pushed branches, delete no worktree (list them in the report), keep reading the ledger, then post one morning report. Unclear which: treat as stop and ask once. `resumed` clears either.
- `stop-at` is the hard stop (the first such clock time after the run starts): nothing dispatched or merged after it; fix rounds and re-reviews count as dispatches; in-flight work may finish into a PR. The run also ends when no dispatchable ticket remains, and on `stopped`.
- Fail closed when `gh` login is gone, the tracker is unreachable twice in a row, or every worker start fails: append `stopped` with the reason, post one report (final reply if the tracker is unreachable), no wake-up, no retry until morning.
- Never edit a `forbidden-files` path, the workers' skills, or permissions during a run. The one exception is the evidence Draft PR (`reference/contracts.md`).

## Decisions for workers

Worker questions reach you (the implementer's `QUESTION` rule: `reference/contracts.md`; asking adds no ledger state); answer from the Spec. **You decide**: implementation detail, a gap with an obvious default, code style, test seams; write the answer and its Spec basis in the ticket comment. **The operator decides in the morning** (ticket blocked, the ledger says what to choose): a Spec change, adding or removing a feature, data changes outside the schema, money, email, anything sent outside the system.

## Morning report

When the run ends, post the report as `reference/morning-report.md` says. Contracts for `list-tickets` and the three roles: `reference/contracts.md`.

## Failure to avoid

Orchestrators drift into doing the work. When you catch yourself reading a diff to judge it, writing code, or editing a ticket's scope, dispatch instead.
